# PRD: Транскрибация записей встреч через локальный Whisper

**Дата**: 2026-09-07

**Статус**: Draft

## Цель

Заменить заглушку распознавания речи (`StubSttService`) реальной локальной транскрибацией
аудио через `whisper.cpp` с моделью `tiny`. После загрузки записи встречи (`recording`)
пользователь получает настоящий текстовый транскрипт сказанного, а до его готовности видит
статус обработки на странице встречи. Инфраструктура вокруг (фоновая очередь, поле
`transcriptText`, статусы `pending → processing → done | failed`, ручной `reprocess`,
UI со списком файлов и поллингом статуса) уже реализована предыдущей фазой и переиспользуется
без изменений контракта.

## Пользовательский сценарий

- Пользователь загружает на странице встречи аудио/видео запись → файл появляется в списке со
  статусом «Обрабатывается», фоновая задача стартует автоматически (как сейчас).
- В фоне API конвертирует файл в 16 кГц моно WAV через `ffmpeg` и запускает `whisper.cpp`
  с моделью `tiny` → по завершении в записи файла сохраняется распознанный текст.
- Статус в UI сам меняется на «Готово» (существующий поллинг, без перезагрузки) → пользователь
  разворачивает блок транскрипта и видит реальный текст встречи.
- Whisper или конвертация падает (нет бинарника/модели, битый звук, таймаут, пустой вывод) →
  статус «Ошибка», рядом кнопка «Повторить» → повтор перезапускает реальную транскрибацию.
- Загружены две записи подряд → они распознаются последовательно (один воркер): вторая остаётся
  «Обрабатывается»/в очереди, пока не завершится первая.

## В скоупе

- Новая реализация `SttService` — `WhisperSttService`: вызывает бинарник `whisper.cpp` как
  подпроцесс (`child_process`, без Python), парсит stdout/файл вывода в plain-text транскрипт.
- Конвертация входного файла в 16 кГц моно 16-bit WAV через `ffmpeg` (подпроцесс) во временный
  файл перед запуском Whisper; временный файл удаляется в `finally` (и при успехе, и при ошибке).
- Модель `tiny` (ggml/gguf) — путь к бинарнику и модели задаются через env; сама модель в git
  не коммитится (`.gitignore` + скрипт/документированная команда для её загрузки в нужный путь).
- Язык распознавания через env `WHISPER_LANGUAGE`: не задан → авто-детект; задан (например `ru`) →
  принудительный язык. Значение и поведение описаны в `apps/api/.env.example`.
- Расширение `SttInput`: движку передаётся `storageKey` (или путь) загруженного файла, чтобы
  читать реальные байты, а не только метаданные. Правка затрагивает `MeetingFileProcessingQueue`,
  `StubSttService` и e2e-фейк STT.
- Доступ движка к пути файла на диске: `FileStorageService` получает метод выдачи абсолютного пути
  (или копирования во временный файл) для передачи в подпроцесс.
- Выбор движка через env `STT_ENGINE` (`whisper` | `stub`), дефолт `whisper`; `stub` остаётся для
  локальной разработки без установленного Whisper и для тестов. DI-биндинг в `MeetingFileModule`
  выбирает провайдера по `STT_ENGINE`.
- Таймаут транскрибации `WHISPER_TIMEOUT_MS` (env): по превышении подпроцесс убивается, статус
  файла → `failed`, очередь не залипает.
- Завершение работы: запущенный подпроцесс Whisper/ffmpeg убивается при остановке приложения
  (`OnModuleDestroy` очереди), чтобы `app.close()` в e2e не висел и не оставлял «сирот».
- Обработка ошибок → статус `failed` без частичного `transcriptText`: нет бинарника, нет модели,
  нет `ffmpeg`, ненулевой код выхода Whisper/ffmpeg, таймаут, пустой/пробельный транскрипт,
  неподдерживаемый/битый звук.
- Unit-тесты `WhisperSttService` (`pnpm --filter api test`) с замоканным `child_process`: сборка
  аргументов запуска (путь модели, язык, входной путь, формат вывода), парсинг вывода в текст,
  каждая ветка ошибок → брошенное исключение.
- e2e (`pnpm --filter api test:e2e`) остаются на stub через `.overrideProvider(STT_SERVICE)` —
  бинарник Whisper и `ffmpeg` в CI и pre-commit не требуются.
- Документация тем же PR: `apps/api/.env.example` (новые `WHISPER_*` и `STT_ENGINE`),
  `apps/api/CLAUDE.md` (выбор движка, зависимость от `ffmpeg`, стратегия тестов),
  `src/meeting-file/CLAUDE.md` (если есть) и раздел env в корневом `CLAUDE.md` / `README.md`.

## Не в скоупе

- Изменение контракта статусов: enum `MeetingFileStatus` и путь `pending → processing → done |
failed` остаются как есть; прогресс в процентах, оставшееся время, под-этапы («в очереди» /
  «конвертация» / «распознавание») — не добавляем (осознанное решение: текущих 4 статусов достаточно).
- Диаризация (разметка спикеров), тайм-коды/сегменты, субтитры (SRT/VTT), word-level timestamps.
- Редактирование транскрипта, поиск по нему, суммаризация, извлечение задач, любые LLM-функции.
- Модели крупнее `tiny`, GPU-ускорение, квантизация под конкретное железо.
- Авто-скачивание модели внутри обработки запроса в проде — модель должна быть подготовлена заранее
  (одноразовый setup-скрипт — в скоупе, докачка «на лету» в рантайме — нет).
- Внешние/облачные STT-провайдеры, очередь-брокер, несколько воркеров, распределённая обработка.
- Автоматический ретрай с бэкоффом (ручной `reprocess` для `failed` уже есть).
- Чанковая транскрибация очень длинных файлов, стриминговое распознавание.
- WebSocket / SSE для live-обновления статуса (остаётся существующий поллинг).
- Выбор языка распознавания на каждый файл из UI (только глобальный env).
- Новые функции на странице встречи: блок статуса и разворачиваемый транскрипт уже существуют,
  дорабатываем UI только если реальный движок сломает текущее поведение.

## Технические ограничения

- У `apps/api` нет своего Dockerfile — API запускается как Node-процесс, `docker-compose.yml`
  поднимает только Postgres. Бинарник `whisper.cpp`, модель `tiny` и `ffmpeg` должны присутствовать
  в окружении, где работает API; CI и pre-commit не должны от них зависеть (stub в e2e, мок
  `child_process` в unit-тестах).
- `whisper.cpp` принимает только 16 кГц моно 16-bit WAV, а загрузки бывают mp3/m4a/webm/ogg/mp4/mov
  (см. `ALLOWED_UPLOAD_MIME_TYPES`) → обязательна конвертация через `ffmpeg` во временный файл с
  гарантированной очисткой.
- `FileStorageService` сейчас отдаёт только потоки (`createReadStream`) — подпроцессу нужен путь на
  ФС: нужен аккуратный аксессор абсолютного пути или копирование во временный файл (path traversal
  барьер `resolvePath` сохраняется).
- `SttInput` сейчас несёт только `originalName` и `size`; добавление `storageKey`/пути — ломающее
  изменение интерфейса, ripple в очередь, stub и e2e-фейк.
- Транскрибация — долгая CPU-операция: очередь остаётся одним воркером (`concurrency = 1`), нужен
  таймаут, и подпроцесс обязан убиваться в `OnModuleDestroy` (иначе висящие e2e и pre-commit).
- Вывод Whisper недетерминирован → ассерты в тестах только на stub, не на реальном движке.
  Проверка реального транскрипта — ручная, на заранее известном коротком аудиосэмпле.
- Файл модели `tiny` (~75 МБ) не коммитится в git: `.gitignore`, setup-скрипт и документированный
  путь (`WHISPER_MODEL_PATH`).
- Захват вывода подпроцесса — в кодировке UTF-8; временные файлы — в `os.tmpdir()` или отдельном
  каталоге с очисткой.
- Опционально: `validateEnv` при `STT_ENGINE=whisper` проверяет наличие бинарника и модели на
  старте — фатально в `production`, предупреждение вне его (по аналогии с проверкой `JWT_SECRET`).
- Все правки в рамках существующих эндпоинтов под `JwtAuthGuard` — новых HTTP-ручек нет, миграция
  Prisma не требуется.

## Критерии готовности

- [ ] При `STT_ENGINE=whisper` загрузка короткой реальной аудиозаписи проводит файл
      `pending → processing → done`, и `transcriptText` содержит реально произнесённые слова
      (проверено вручную на известном сэмпле), а не строку заглушки.
- [ ] `whisper.cpp` вызывается как подпроцесс с моделью `tiny`; в рантайме API нет Python.
- [ ] Запись не в формате WAV (mp3/m4a/webm/mp4) успешно транскрибируется (происходит конвертация
      через `ffmpeg`); после `done` и после `failed` в каталоге загрузок и во временном каталоге
      не остаётся WAV-файлов.
- [ ] `WHISPER_LANGUAGE` не задан → язык определяется автоматически; задан `ru` → распознавание
      принудительно на русском; поведение и пример описаны в `apps/api/.env.example`.
- [ ] Каждый из сбоев переводит файл в `failed` без частичного `transcriptText`, и последующий
      `POST /meetings/:id/files/:fileId/reprocess` перезапускает обработку: нет бинарника, нет
      модели, нет/падает `ffmpeg`, ненулевой код выхода Whisper, превышен `WHISPER_TIMEOUT_MS`,
      пустой транскрипт.
- [ ] При `STT_ENGINE=stub` (и в e2e через override) поведение и тексты транскрипта — прежние,
      заглушечные.
- [ ] Идущая транскрибация убивается при остановке приложения: `app.close()` в `afterEach` e2e не
      висит, процессов-сирот `whisper`/`ffmpeg` не остаётся.
- [ ] Очередь остаётся одним воркером: две записи, загруженные подряд, транскрибируются
      последовательно — вторая не уходит в `processing`, пока первая не `done`/`failed`.
- [ ] `pnpm --filter api test` содержит тесты `WhisperSttService` с замоканным `child_process`:
      корректные аргументы запуска, парсинг вывода в текст, каждая ветка ошибок → исключение.
- [ ] `pnpm --filter api test:e2e` проходит с поднятым Postgres на stub-движке — бинарник Whisper
      и `ffmpeg` в CI не нужны.
- [ ] На странице встречи запись показывает «Обрабатывается» во время работы Whisper и реальный
      разворачиваемый транскрипт после `done`; статус обновляется существующим поллингом без
      перезагрузки (проверено в браузере).
- [ ] `.env.example` документирует `STT_ENGINE`, `WHISPER_BIN_PATH`, `WHISPER_MODEL_PATH`,
      `WHISPER_LANGUAGE`, `WHISPER_TIMEOUT_MS`; есть скрипт или документированная команда загрузки
      модели `tiny` в `WHISPER_MODEL_PATH`; файл модели добавлен в `.gitignore`.
- [ ] Обновлены `apps/api/CLAUDE.md` (выбор движка, зависимость от `ffmpeg`, стратегия тестов),
      `src/meeting-file/CLAUDE.md` при наличии, и раздел переменных окружения в корневом `CLAUDE.md`
      и `README.md`.
