# Технический ресёрч плана

Прочитай план из файла: $ARGUMENTS

Задача — не писать код, а разобрать, **как** оптимально реализовать план технически: по каждой спорной точке дать варианты, компромиссы и обоснованную рекомендацию, строго в границах плана и с опорой на документацию проекта.

Сохрани результат в файл `docs/research-<slug>.md`, где `<slug>` — имя файла плана без пути, расширения и префикса `plan-` (например план `plan/plan-meeting-file-upload.md` -> ресёрч `docs/research-meeting-file-upload.md`). Slug уже на английском и в kebab-case — не меняй его, только замени префикс `plan-` на `research-`.

Если нет папки `docs` — создай.

## Порядок действий

1. Прочитай план и связанный с ним PRD (ссылка в шапке плана). Выпиши все технические решения, которые план оставляет открытыми (по фазам и областям: database / backend / frontend).
2. **Прочитай документацию проекта до разбора вариантов** (это обязательный шаг):
   - корневой `CLAUDE.md` и `README.md`;
   - `apps/*/CLAUDE.md` каждого затронутого планом пакета;
   - `.env.example` затронутых пакетов, `docker-compose.yml`, `turbo.json`.
3. Сверься с релевантными skill-библиотеками правил проекта:
   - backend/NestJS — `nestjs-best-practices`;
   - frontend/React/Next.js — `vercel-react-best-practices`;
   - UI на HeroUI — `heroui-react`; UX/вёрстка — `ui-ux-pro-max`.
4. Изучи существующий код на предмет уже принятых паттернов (CQRS-структура фичи, `JwtAuthGuard`, Prisma-адаптер, форма e2e-спеков, слой `src/lib/api.ts`, защита страниц сессией). Новое решение должно повторять эти паттерны, а не вводить свой стиль.
5. Для каждого открытого вопроса разбери варианты и выбери один — по структуре ниже.
6. Собери итоговые рекомендации и открытые вопросы, запиши файл.

## Структура документа

# Research: {имя файла ресёрча}

**План:** $ARGUMENTS
**PRD:** {ссылка на PRD из шапки плана}
**Дата:** {текущая дата}

## Контекст из документации проекта
Ключевые ограничения и соглашения, релевантные плану, со ссылками на источник (`файл:строка` или пункт `CLAUDE.md`). Например: ESM с расширением `.js` в импортах, Prisma 7 без rust-движка, один `CqrsModule.forRoot()`, детерминированные e2e без внешних сервисов, локальный диск для файлов.

## Открытые технические вопросы
Нумерованный список решений, которые нужно принять, сгруппированный по фазам плана.

## Разбор вариантов

### {Вопрос / область}
**Что требует:** пункт плана / критерий PRD, порождающий этот выбор.
**Варианты:**
1. {Вариант} — плюсы / минусы, стоимость, влияние на тесты.
2. {Вариант} — плюсы / минусы.
**Рекомендация:** выбранный вариант и почему именно он в этом проекте.
**Как ложится в проект:** конкретные модули/файлы, какие существующие паттерны и пункты `CLAUDE.md` соблюдаются (со ссылками).
**Зависимости:** новые npm-пакеты (с проверкой ESM-совместимости), env-переменные, миграции Prisma, тома в `docker-compose`.
**Риски:** что может пойти не так, последствия для e2e и pre-commit хука.

## Итоговые рекомендации
По каждой фазе плана — выбранный технический подход одной-двумя строками.

## Открытые вопросы
- Вопросы, требующие решения пользователя (пробелы и противоречия в плане, выбор без явного победителя).

## Правила

- Сначала документация и существующий код, потом рекомендации. Каждая рекомендация обоснована и учитывает ограничения проекта (ESM, Prisma 7, in-process без брокера, локальный диск, детерминированные e2e, JWT-guard на всех приватных эндпоинтах).
- Ссылайся на конкретику: `файл:строка`, пункт `CLAUDE.md`, правило skill-библиотеки. Без общих слов.
- Не переписывай план и не меняй скоуп — разбираешь только «как», в границах плана.
- Не предлагай то, что PRD явно вынес в «Не в скоупе».
- Минимум новых зависимостей. Для каждой — зачем она нужна, чем плоха альтернатива на стандартной библиотеке / уже установленном пакете, и что она работает в чистом ESM.
- Предпочитай решение, повторяющее существующий паттерн проекта, даже если «в вакууме» есть более модное.
- Пробел или противоречие в плане — в «Открытые вопросы», не выдумывай ответ.
- Если план непонятен без контекста — задай уточняющие вопросы до создания файла.
