# Ralph loop - правила автономной работы

### Как брать Issues
- Номер Issue уже передан тебе в промпте (#{issue}) скриптом ralph-loop.js - не выбирай issue сам, не бери другую
- Читай title, body и критерий готовности именно этой issue
- Ветка для milestone (`feature/<англ-slug-названия>-phase-<номер фазы>`, напр. `feature/api-password-change-phase-2`) уже создана от baseBranch и переключена скриптом ralph-loop.js до твоего запуска - её имя передано в промпте ({branch})
- Работай только в этой ветке - не создавай и не переключай другие

## Именование коммитов
- По правилам в skill commit

## Правила реализаци
- Сначала тесты - потом реализация (TDD)
- После каждого финального изменения запускай тесты
- Если тесты красные после 5 попыток - остановись и напиши в Issue комментарий с описание проблемы

## Экономия контекста (важно - каждый лишний токен стоит денег)
- В plan-файле читай ТОЛЬКО раздел своей фазы (по заголовку `### Фаза N`), не весь файл
- Не перечитывай файлы, которые уже есть в твоём контексте
- Точечные `grep`/`rg` по нужному символу вместо чтения файлов целиком
- Итерации одной фазы идут в одной сессии (`--resume`) - контекст с прошлой issue уже прогрет, не повторяй разведку

## Проверка UI (только для веб-фаз, где затронут интерфейс)
- Снимай ОДИН `browser_snapshot` на каждое проверяемое состояние, не после каждого клика
- Максимум 3 скриншота на issue (напр. светлая+десктоп, тёмная+моб, состояние ошибки)
- `browser_console_messages` - один раз в конце проверки
- Не гоняй сборку (`build`) в цикле - достаточно `lint` + `typecheck`

## Правила завершения
- Убедись что все тесты зелёные
- Убедись что все требования выполнены
- Быстрая самопроверка диффа: соответствие issue, стандартам репозитория (CLAUDE.md), отсутствие мусора и лишнего scope. Полное ревью двумя субагентами (`/code-review`) на каждую issue НЕ запускай - его делает ralph-loop.js один раз на весь milestone после создания PR
- Закрой Issue
- Не создавай PR это сделает ralph-loop.js после закрытия последней Issue в milestone
