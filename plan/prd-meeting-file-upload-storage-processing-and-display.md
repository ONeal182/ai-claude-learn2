# Plan: prd-meeting-file-upload-storage-processing-and-display

**PRD:** @docs/prd-meeting-file-upload-storage-processing-and-display.md
**Дата:** 2026-09-02

**Подход к тестам:** в каждой фазе тесты пишутся до реализации (красные), реализация ведётся до их позеленения. Автоматический e2e-раннер есть только в `apps/api` (`pnpm --filter api test:e2e`, vitest, нужен поднятый Postgres) — им покрываются бэкенд-фазы и API-контракт, который потребляют веб-страницы. UI веб-фаз проверяется через Playwright MCP + ревью по скиллу `ui-ux-pro-max` (браузерного тест-раннера в проекте нет — вне скоупа PRD).

## Фазы реализации

### Фаза 1: Бэкенд — хранение файлов встречи (Tracer Bullet)
**Цель:** к встрече можно приложить файл (запись или вложение): он сохраняется на диск, метаданные — в БД, доступны список, скачивание и удаление.
**Затрагивает:** database, backend

**Задачи:**
- [ ] Написать e2e `test/meeting-files.e2e-spec.ts` до реализации (красные): загрузка `attachment` (→ `done`) и `recording` (→ `pending`) под Bearer с проверкой метаданных (исходное имя, размер, mime); отказы — без JWT (401), сверх лимита размера (413), mime не из белого списка (400), несуществующая встреча (404); `GET /meetings/:id/files`; `GET /meetings/:id/files/:fileId/content` (проверка `Content-Type` и `Content-Disposition`); `DELETE /meetings/:id/files/:fileId` + повторный `DELETE` → 404
- [ ] Prisma-модель `MeetingFile` (связь с `Meeting`; `type` = `recording | attachment`; `status` = `pending | processing | done | failed`; метаданные: исходное имя, размер, mime, дата загрузки; путь/ключ в хранилище) + миграция Prisma
- [ ] `POST /meetings/:id/files` — multipart под `JwtAuthGuard`: лимит размера тела (413), белый список mime (400), 404 для несуществующей встречи; бинарник в папку `uploads`, метаданные и путь в БД, статус `done` для `attachment` / `pending` для `recording`
- [ ] `GET /meetings/:id/files` (список с типом, статусом, метаданными), `GET /meetings/:id/files/:fileId/content` (отдача файла с корректными заголовками), `DELETE /meetings/:id/files/:fileId` (удаление записи и бинарника)
- [ ] Env-переменные (путь до `uploads`, лимит размера файла) в `apps/api/.env.example`, том `uploads` в `docker-compose`, актуализация `apps/api/CLAUDE.md`; прогон `pnpm --filter api test:e2e` — спеки из первой задачи зелёные

**Когда готова:** `pnpm --filter api test:e2e` зелёный с поднятым Postgres; e2e фазы покрывают загрузку обоих типов, отказы 401 / 413 / 400 / 404, список, скачивание с верными заголовками, удаление (повторный `DELETE` → 404); бинарник лежит на диске, в БД — только путь.

### Фаза 2: Бэкенд — фоновая обработка записи и транскрипт
**Цель:** файл типа `recording` после загрузки автоматически обрабатывается in-process воркером, по завершении доступен транскрипт; упавшую обработку можно перезапустить вручную.
**Затрагивает:** backend

**Задачи:**
- [ ] Дописать e2e в `test/meeting-files.e2e-spec.ts` до реализации (красные): `recording` детерминированно проходит `pending → processing → done` без дополнительного вызова и отдаёт связанный текстовый транскрипт; `POST /meetings/:id/files/:fileId/reprocess` перезапускает только файл в статусе `failed`, для остальных статусов — ошибка; `DELETE` файла удаляет и его транскрипт
- [ ] In-process очередь/воркер внутри API (без внешнего брокера) + детерминированная заглушка STT для тестового окружения
- [ ] Автозапуск обработки для файла типа `recording` сразу после успешной загрузки; статус `pending → processing → done`, при ошибке → `failed`; сохранение транскрипта как артефакта, связанного с файлом (доступ полем в ответе `GET /meetings/:id/files` или отдельным эндпоинтом)
- [ ] `POST /meetings/:id/files/:fileId/reprocess` — только для статуса `failed`; дополнить `DELETE /meetings/:id/files/:fileId` удалением артефактов обработки
- [ ] Актуализация `apps/api/CLAUDE.md`; прогон `pnpm --filter api test:e2e` — новые спеки зелёные, спеки фазы 1 не сломаны

**Когда готова:** `pnpm --filter api test:e2e` зелёный; загруженная `recording` без дополнительного вызова доходит до `done` с доступным транскриптом; `reprocess` работает только для `failed`, на прочих статусах отвечает ошибкой; удаление файла удаляет и его транскрипт.

### Фаза 3: Веб — страница встречи и переход с дашборда
**Цель:** появляется страница `/meetings/[id]` с заголовком и временем встречи, на неё можно перейти из списка встреч на дашборде.
**Затрагивает:** backend (только e2e), frontend

**Задачи:**
- [ ] До правок фронтенда убедиться, что e2e покрывают `GET /meetings/:id` (200 с `id` / `title` / `startsAt`, 404 для несуществующей встречи, 401 без JWT); дополнить `test/meeting.e2e-spec.ts` при пробелах
- [ ] `src/lib/api.ts` — метод `getMeeting(id, token)` (`GET /meetings/:id` с `Authorization: Bearer`), обработка `ApiError`
- [ ] Страница `/meetings/[id]` (App Router) — детали встречи (заголовок, время); состояния loading / ошибка / 404; защита сессией как в `Dashboard` (нет сессии → `/login`, `401` → чистка сессии и `/login`)
- [ ] Переход на страницу встречи со списка встреч на дашборде (`MeetingRow` → навигация)
- [ ] Проверка UI через Playwright MCP (светлая/тёмная тема, мобильная/десктопная ширина, состояние 404, отсутствие ошибок в консоли) + ревью по скиллу `ui-ux-pro-max`; тексты на русском, стиль согласован с дашбордом (HeroUI v3, Tailwind v4); обновление `apps/web/CLAUDE.md` (новый роут `/meetings/[id]`)

**Когда готова:** `pnpm --filter api test:e2e` зелёный; с дашборда клик по встрече открывает `/meetings/[id]` с её заголовком и временем; страница проверена в браузере в обеих темах и на обеих ширинах, консоль чистая, тексты на русском.

### Фаза 4: Веб — блок «Файлы» на странице встречи
**Цель:** на странице встречи можно загружать файлы с прогрессом, видеть их список со статусом обработки, скачивать/удалять/перезапускать обработку и разворачивать транскрипт; статус обновляется без перезагрузки.
**Затрагивает:** backend (только e2e), frontend

**Задачи:**
- [ ] До правок фронтенда дополнить API-e2e сквозным сценарием пути UI (если не покрыт фазами 1–2): загрузка → список со статусом → появление транскрипта для `recording` → скачивание → `reprocess` для `failed` → удаление
- [ ] `src/lib/api.ts` — методы: список файлов встречи, загрузка (multipart с индикацией прогресса через `XMLHttpRequest`), скачивание, удаление, `reprocess`
- [ ] Блок «Файлы» на странице встречи: зона загрузки (drag-n-drop и выбор файла), индикатор прогресса, отображение ошибок загрузки (413 / 400 / сеть)
- [ ] Список загруженных файлов со статусом обработки и действиями «Скачать», «Удалить», «Повторить» (последнее — только для `failed`); отображение транскрипта готовой записи со сворачиванием/разворачиванием; обновление статуса без перезагрузки (поллинг или явная кнопка обновления)
- [ ] Проверка UI через Playwright MCP (темы, ширины, состояния: прогресс, ошибка загрузки, пустой список, `failed` с «Повторить», развёрнутый транскрипт, обновление статуса) + ревью по `ui-ux-pro-max`; тексты на русском; обновление `apps/web/CLAUDE.md`

**Когда готова:** `pnpm --filter api test:e2e` зелёный; на странице встречи файл перетаскивается или выбирается, показывается прогресс, затем файл в списке со статусом; `recording` уходит в обработку и по завершении показывает сворачиваемый транскрипт; статус обновляется без перезагрузки; «Скачать» и «Удалить» работают для любого файла, «Повторить» — только для `failed`; UI проверен в браузере в обеих темах и на обеих ширинах.
