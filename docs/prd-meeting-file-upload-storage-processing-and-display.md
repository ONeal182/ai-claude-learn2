# PRD: Загрузка и отображение файлов встречи

**Дата**: 2026-09-02

**Статус**: Draft

## Цель

Дать возможность прикреплять к встрече файлы — аудио/видео запись самой встречи и произвольные вложения (слайды, PDF, изображения, заметки), — чтобы они надёжно хранились, запись автоматически уходила в фоновую обработку (транскрипт), а все материалы и результат обработки были видны на странице встречи. Сейчас встреча содержит только заголовок и время, приложить к ней материалы нельзя.

## Пользовательский сценарий

- Пользователь открывает встречу из списка → попадает на страницу встречи с деталями и блоком «Файлы» (пустым, если ничего не загружено).
- Пользователь перетаскивает или выбирает аудио/видео запись → файл загружается с индикатором прогресса → появляется в списке со статусом «Обрабатывается».
- Пользователь загружает вложение (PDF, слайды, изображение) → файл появляется в списке со статусом «Готово», без обработки.
- Фоновая обработка записи завершается → статус меняется на «Готово», на странице встречи доступен транскрипт.
- Обработка падает → статус «Ошибка», рядом кнопка «Повторить».
- Пользователь скачивает любой загруженный файл по клику.
- Пользователь удаляет ошибочно загруженный файл → файл и его артефакты обработки удаляются.

## В скоупе

- Модель файла встречи, привязанная к `Meeting`: тип (`recording` | `attachment`), статус обработки, метаданные (исходное имя, размер, mime, дата загрузки), путь/ключ в хранилище.
- Эндпоинт загрузки файла во встречу (multipart), под `JwtAuthGuard`; ограничение размера тела и белый список mime.
- Хранение бинарных файлов на локальном диске / томе (папка `uploads`); в БД — только метаданные и путь, сам файл вне БД.
- Эндпоинты: список файлов встречи, скачивание файла, удаление файла.
- Автозапуск фоновой задачи обработки для файлов типа `recording` сразу после успешной загрузки, без отдельного вызова.
- Обработка `recording` → текстовый транскрипт, сохраняется и связывается с файлом; статусы `pending → processing → done | failed`.
- Ручной повтор обработки (`reprocess`) для файла в статусе `failed`.
- Веб: новая страница `/meetings/[id]` — детали встречи (заголовок, время) + блок файлов.
- Веб: зона загрузки (drag-n-drop и выбор файла), индикатор прогресса, обработка ошибок загрузки.
- Веб: список загруженных файлов со статусом обработки и действиями «Скачать», «Удалить», «Повторить» (для `failed`).
- Веб: отображение транскрипта готовой записи на странице встречи (сворачивается/разворачивается).
- Веб: переход на страницу встречи со списка встреч на дашборде.
- Веб: обновление статуса обработки без перезагрузки страницы (поллинг или явная кнопка обновления).

## Не в скоупе

- Реальный движок распознавания речи / интеграция с внешним STT — обработка может быть заглушкой; важен контракт статусов и артефакта-транскрипта.
- Редактирование транскрипта, разметка спикеров, поиск по транскрипту.
- Суммаризация, извлечение задач и любые LLM-функции поверх транскрипта.
- Облачное / S3 хранилище, CDN, подписанные ссылки с TTL.
- Возобновляемая / чанковая загрузка больших файлов, докачка после обрыва.
- Встроенный аудио/видео плеер и предпросмотр вложений в интерфейсе (достаточно скачивания).
- Версионирование файлов, корзина, восстановление удалённых.
- Разграничение доступа между пользователями, шаринг встречи, роли.
- WebSocket / SSE для live-обновления статуса.
- Антивирусная проверка загружаемых файлов.

## Технические ограничения

- Текущая модель `Meeting` содержит только `id` / `title` / `startsAt`; страницы встречи в `apps/web` нет — её нужно создать.
- Хранилище — локальный диск: том в `docker-compose` для контейнера API. При нескольких инстансах API файлы не будут общими — ограничение принято осознанно для этой итерации.
- Загрузка идёт через API (NestJS 12, ESM); нужен multipart-парсер и лимит размера тела, согласованный с reverse-proxy.
- Обработка фоновая, вне HTTP-запроса. В текущем стеке нет брокера очередей — допустима in-process очередь/воркер внутри API.
- Нужна миграция Prisma для новой таблицы; `prisma migrate deploy` и e2e гоняются в CI и в pre-commit хуке и требуют поднятого Postgres.
- E2e-тесты не должны зависеть от внешнего STT — обработка в тестовом окружении должна быть детерминированной (заглушка).
- Все новые эндпоинты — под `JwtAuthGuard` и Bearer JWT, как существующий `/meetings`.
- Новые env-переменные (путь до `uploads`, лимит размера) фиксируются в `apps/api/.env.example`; документация правится тем же PR (правило `CLAUDE.md`).

## Критерии готовности

- [ ] `POST /meetings/:id/files` принимает multipart-файл; отклоняет запрос без валидного JWT (401), файл сверх лимита размера (413), mime не из белого списка (400), несуществующую встречу (404).
- [ ] После успешной загрузки в БД создаётся запись файла со статусом `pending` (для `recording`) или `done` (для `attachment`) и корректными метаданными: исходное имя, размер, mime.
- [ ] Бинарный файл сохраняется на диск / том, а не в БД; в записи хранится только путь/ключ.
- [ ] `GET /meetings/:id/files` возвращает список файлов встречи с типом, статусом и метаданными.
- [ ] `GET /meetings/:id/files/:fileId/content` отдаёт исходный файл с корректными `Content-Type` и `Content-Disposition`.
- [ ] `DELETE /meetings/:id/files/:fileId` удаляет запись, бинарный файл и артефакты обработки; повторный запрос возвращает 404.
- [ ] Для файла типа `recording` фоновая обработка стартует автоматически после загрузки, без дополнительного вызова.
- [ ] Статус файла проходит путь `pending → processing → done`; при ошибке обработки становится `failed`.
- [ ] По завершении обработки `recording` доступен связанный с файлом текстовый транскрипт (отдельным эндпоинтом или полем в ответе списка).
- [ ] `POST /meetings/:id/files/:fileId/reprocess` перезапускает обработку только для файла в статусе `failed`; для остальных статусов возвращает ошибку.
- [ ] Есть миграция Prisma для новой таблицы; `pnpm --filter api test:e2e` проходит с поднятым Postgres.
- [ ] E2e покрывают: успешную загрузку `recording` и `attachment`, отказы по размеру / mime / авторизации, список, скачивание, удаление.
- [ ] В `apps/web` открывается страница `/meetings/[id]` с заголовком и временем встречи; со списка встреч на дашборде есть переход на неё.
- [ ] На странице встречи есть зона загрузки (drag-n-drop и выбор файла) с индикатором прогресса и отображением ошибок загрузки.
- [ ] Загруженные файлы отображаются списком со статусом обработки; доступны действия «Скачать», «Удалить» и «Повторить» (последнее — только для `failed`).
- [ ] Транскрипт готовой записи показывается на странице встречи и сворачивается/разворачивается.
- [ ] Статус обработки в UI обновляется без перезагрузки страницы (поллинг или явная кнопка обновления).
- [ ] Тексты интерфейса на русском, визуальный стиль согласован с текущим дашбордом (HeroUI v3, Tailwind v4).
- [ ] Обновлены `apps/api/CLAUDE.md`, `apps/web/CLAUDE.md` и `apps/api/.env.example` (новые переменные: путь до `uploads`, лимит размера файла).
