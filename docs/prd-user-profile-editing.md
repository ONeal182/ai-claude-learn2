# PRD: Страница профиля и редактирование профиля

**Дата**: 2026-09-04

**Статус**: Draft

## Цель

Дать залогиненному пользователю страницу профиля и страницу редактирования, где он может сменить отображаемое имя, загрузить аватар и сменить пароль (с подтверждением старого). Аватар и имя показываются на странице профиля и в шапке дашборда, где сейчас выводится только email.

## Пользовательский сценарий

- Пользователь кликает по аватару/имени в шапке дашборда -> открывается `/profile` с аватаром (или инициалами), именем (или email, если имя не задано), email и датой регистрации.
- Пользователь нажимает «Редактировать» на `/profile` -> открывается `/profile/edit` с формой.
- Пользователь меняет имя и сохраняет -> новое имя видно на `/profile` и в шапке дашборда.
- Пользователь выбирает файл аватара -> видит превью до отправки -> сохраняет -> новый аватар виден на `/profile` и в шапке дашборда.
- Пользователь вводит старый пароль, новый пароль и подтверждение, сохраняет -> при верном старом пароле пароль сменён, пользователь остаётся залогинен; при неверном старом — ошибка у формы, пароль не изменён.
- Неавторизованный пользователь открывает `/profile` или `/profile/edit` -> редирект на `/login` (как у дашборда).

## В скоупе

**API (`apps/api`)**

- Prisma: на модель `User` добавить `name String?` и `avatarKey String?` + миграция.
- `GET /users/me` (под `JwtAuthGuard`) -> `{ id, email, name, avatarUrl, createdAt }` (`name`/`avatarUrl` = `null`, пока не заданы).
- `PATCH /users/me` (под `JwtAuthGuard`) — смена имени. Валидация: trim, длина 1..50; невалидное -> 400.
- `POST /users/me/password` (под `JwtAuthGuard`) — тело `{ currentPassword, newPassword }`. Проверка `currentPassword` через bcrypt; `newPassword` — минимальная длина как при регистрации. Токен не отзывается.
- `PUT /users/me/avatar` (под `JwtAuthGuard`, multipart, поле `file`) — загрузка/замена аватара. Белый список mime `image/jpeg|image/png|image/webp`, лимит 5 МБ (отдельный `MulterModule`). При замене старый файл удаляется с диска. Ответ содержит новый `avatarUrl`.
- `GET /users/avatars/:key` — публичная (без `JwtAuthGuard`) отдача бинарника аватара по неугадываемому ключу с корректным `Content-Type`.
- Хранение — через существующий `FileStorageService` (плоская раскладка `${UPLOADS_DIR}/${key}`, ключ — случайный uuid).
- CQRS: команды/запросы через шину, хендлеры в `UsersModule` (или новом модуле профиля).

**Веб (`apps/web`)**

- Страница `/profile` — под клиентским guard'ом (редирект на `/login` при отсутствии сессии), карточка: аватар или инициалы, имя или email, email, дата регистрации, кнопка «Редактировать» -> `/profile/edit`.
- Страница `/profile/edit` — форма из трёх блоков: имя (одно поле + сохранить); аватар (выбор файла + превью + сохранить); смена пароля (старый / новый / подтверждение + сохранить). Ошибки и успех показываются у соответствующего блока.
- Шапка дашборда (`components/dashboard.tsx`): аватар (или инициалы) + имя (или email) вместо текущего «Вы вошли как {email}», кликабельно -> `/profile`.
- `lib/api.ts`: функции `getMe`, `updateProfileName`, `uploadAvatar`, `changePassword`.
- Данные профиля (имя, аватар) грузятся из `GET /users/me`, а не из localStorage.
- Обновить `apps/api/CLAUDE.md` и `apps/web/CLAUDE.md` (новые эндпоинты и роуты) в том же PR.

## Не в скоупе

- Смена email.
- Восстановление/сброс пароля по почте («забыли пароль»).
- Отзыв JWT, «выйти со всех устройств».
- Обрезка (crop) аватара и серверный ресайз/сжатие изображения.
- Уникальность имени, никнеймы, @-хендлы.
- Сброс имени обратно в `null` через UI.
- Удаление аккаунта.
- Аватары из внешних сервисов (Gravatar, OAuth).
- Показ аватара где-либо ещё, кроме `/profile` и шапки дашборда (в списках встреч, у авторов файлов и т.п.).
- Поле «имя» в форме регистрации.
- История изменений профиля, аудит.

## Технические ограничения

- Модель `User` сейчас содержит только `id`, `email`, `password`, `createdAt`, `updatedAt` — нужна миграция Prisma (`name String?`, `avatarKey String?`).
- Эндпоинта текущего пользователя нет; веб доверяет email из localStorage. Профиль должен читаться из нового `GET /users/me`.
- `<img>` в шапке не отправляет заголовок `Authorization` — бинарник аватара отдаётся публично по неугадываемому ключу (как `storageKey` у файлов встречи), не под `JwtAuthGuard`.
- Хранилище — локальная ФС через `FileStorageService`; пользовательский ввод в путь не попадает (ключ — случайный uuid).
- Лимит размера и белый список mime для аватара задаёт отдельный `MulterModule` (5 МБ; `image/jpeg`, `image/png`, `image/webp`) -> 413 / 400.
- При замене аватара старый файл удаляется с диска (`FileStorageService.remove`).
- Хеширование пароля — `bcryptjs`, 10 salt rounds (как в `RegisterHandler`).
- Смена пароля не инвалидирует текущий JWT (механизма отзыва нет) — пользователь остаётся залогинен.
- API построен на CQRS: команды/запросы идут через шину, хендлеры регистрируются как провайдеры модуля.
- Next.js App Router: guard страниц — клиентский редирект на `/login` при отсутствии сессии, как в `Dashboard`.
- При замене аватара URL должен меняться (новый ключ), иначе `<img>` покажет старую картинку из кэша браузера.

## Критерии готовности

- [ ] Миграция Prisma добавляет `users.name` (nullable) и `users.avatar_key`/`avatarKey` (nullable); `prisma migrate deploy` проходит на чистой БД.
- [ ] `GET /users/me` с валидным Bearer -> 200 и тело `{ id, email, name, avatarUrl, createdAt }`; у пользователя без правок `name` и `avatarUrl` равны `null`.
- [ ] `GET /users/me` без токена -> 401.
- [ ] `PATCH /users/me` с `{ name: "Иван" }` и валидным Bearer -> 200; следующий `GET /users/me` возвращает `name: "Иван"`.
- [ ] `PATCH /users/me` с `name` из одних пробелов или длиной > 50 -> 400; значение в БД не меняется.
- [ ] `PUT /users/me/avatar` с `image/png` ≤ 5 МБ -> 200 и `avatarUrl`; `GET` по этому URL отдаёт картинку с корректным `Content-Type`; `GET /users/me` возвращает тот же `avatarUrl`.
- [ ] `PUT /users/me/avatar` с файлом > 5 МБ -> 413; с не-`image/*` (например `application/pdf`) -> 400; аватар не меняется.
- [ ] Повторный `PUT /users/me/avatar` заменяет аватар: новый URL отдаёт новую картинку, старый URL -> 404 (файл удалён с диска).
- [ ] `POST /users/me/password` с верным `currentPassword` и валидным `newPassword` -> 200; вход со старым паролем -> 401, вход с новым -> 200.
- [ ] `POST /users/me/password` с неверным `currentPassword` -> 401/400; вход со старым паролем всё ещё -> 200.
- [ ] `POST /users/me/password` с `newPassword` короче минимальной длины -> 400.
- [ ] После смены пароля тот же `accessToken` продолжает работать: `GET /users/me` с ним -> 200.
- [ ] `/profile` без сессии -> редирект на `/login`; с сессией -> показаны аватар (или инициалы), имя (или email, если имя не задано), email и дата регистрации.
- [ ] Кнопка «Редактировать» на `/profile` открывает `/profile/edit`.
- [ ] На `/profile/edit` изменение имени и сохранение -> на экране виден успех, новое имя отображается на `/profile` и в шапке дашборда без ручной перезагрузки (после редиректа/ревалидации).
- [ ] На `/profile/edit` выбор файла аватара показывает превью до отправки; после сохранения новый аватар виден на `/profile` и в шапке дашборда.
- [ ] На `/profile/edit` смена пароля с неверным старым паролем -> ошибка у формы, поля пароля не отправлены повторно автоматически; с верным -> сообщение об успехе, пользователь остаётся на сайте (не разлогинен).
- [ ] В шапке дашборда аватар/имя — ссылка на `/profile`; при отсутствии аватара показаны инициалы (из имени или email).
- [ ] `pnpm lint && pnpm typecheck && pnpm test` проходят; `apps/api/CLAUDE.md` и `apps/web/CLAUDE.md` обновлены новыми эндпоинтами и роутами.
